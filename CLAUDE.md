# CLAUDE.md

## Project overview

`id-translation-project` is a **cookiecutter template** that scaffolds specialized
[`id-translation`](https://github.com/rsundqvist/id-translation) packages for an organization. It is the official
starting point for adopters ("don't greenfield it").

The repo holds two things that must stay in sync:

- **The template** — `{{cookiecutter.project_slug}}/` (Jinja-templated; *not* valid Python on its own).
- **The committed demo** — `demo/bci-id-translation/`, the rendered output (organization "Big Corporation Inc.",
  namespace `big_corporation_inc`, slug `bci-id-translation`). It has its own venv/tooling and is the source for the
  published docs (GitHub Pages).

The sibling library lives at `../id-translation/` (also has a `CLAUDE.md`).

## Bootstrap a new project

```bash
cookiecutter https://github.com/rsundqvist/id-translation-project.git
# or, without installing cookiecutter:
uvx cookiecutter gh:rsundqvist/id-translation-project
```

Prompts (`cookiecutter.json`): `organization` → `namespace` (via `to_namespace`) → `project_slug` (via
`to_slug_prefix`), plus `id_translation_version`. The filters live in `cookiecutter_extensions.py`;
`hooks/post_gen_project.py` prints next steps.

## What a generated project provides

This is the payload — read it before building adoption/onboarding tooling in the library, since it likely already
exists here. Public API is re-exported from `<namespace>.id_translation`:

- **`create_translator()` / `load_cached_translator()`** (`_initialize.py`) — wrap `Translator.from_config` and
  `load_persistent_instance` using the bundled config paths.
- **`get_singleton()` + convenience wrappers** (`singleton/`) — a process-wide cached `Translator` plus
  module-level `translate`, `map`, `map_scores`, `fetch`, `go_offline`, `initialize_sources`, `translated_names`,
  `extract_names` that proxy to it (docstrings auto-generated by `_wrap.py`).
- **`config.py`** — constants: `TRANSLATOR_TYPE`, `IdType`/`NameType`/`SourceType`, `MAIN_CONFIGURATION_PATH`,
  `FETCHING_CONFIGURATION_PATHS` (globs `config/fetching/*.toml`), cache dirs.
- **`customization.py`** — examples of subclassing `Translator` / `SqlFetcher` for behavior TOML can't express.
- **`config/`** — `main.toml`, `metaconf.toml`, `fetching/*.toml` (plus `fetching/inactive/` examples for
  override-only and S3/CSV).
- **`tests/id_translation/test_basics.py`** — builds a translator, resolves sources, and asserts real translation
  output. This **doubles as the config CI gate** — stronger than a "does the config parse" check.
  `tests/conftest.py` hard-fails if the test DB is unreachable.

## Build and run

Tests (here and in a generated project) need the **Sakila** Postgres image:

```bash
docker run -p 5002:5432 --rm rsundqvist/sakila-preload:postgres
# conn: postgresql+pg8000://postgres:Sofia123!@localhost:5002/sakila
```

Template-repo dev env (`uv sync`; tasks in `tasks.py`):

```bash
uv run inv tests        # bake the template into a tmpdir + uv sync + run the generated tests (needs DB)
uv run inv lint         # ruff + template_lint (dev/lint.sh: no leaked concrete values)
uv run inv format       # ruff format + --fix-only
uv run inv generate-demo --replay-file=demo/replay.json  # regenerate demo/bci-id-translation/ (dev/generate-project.sh)
uv run inv backport     # back-port demo edits into the template (dev/backport.py), then lint
uv run inv demo-verify  # run the demo's own ./setup-and-verify.sh pipeline
uv run inv check-links  # opt-in, needs network: template URLs still resolve, anchors included
```

A generated (or the demo) project verifies itself with `./setup-and-verify.sh` (ruff → pytest → mypy → sphinx).

## Key invariants

- **Template ⇆ demo stay in sync.** Edit the template, then regenerate the demo (`dev/generate-project.sh`), or
  back-port demo edits (`dev/backport.py`). `tests/test_demo_in_sync.py` fails CI on any drift.
- **No concrete values in the template.** `dev/lint.py` (entry point `dev/lint.sh`) derives the values to look for
  from the replay files, and separately checks that relative links resolve against the rendered demo — a stale
  namespace in a link matches no derived value.
- **Replay files** (`tests/replay/{stable,default,master}.json`) drive baking. `stable` tests against the released
  `id-translation`; `master` against a local/unreleased checkout. `test_bake_project.py` bakes + installs + runs.
- **Release gate.** `tests/test_demo_replay.py` fails while `demo/replay.json` pins `id_translation_version` to a
  local `file:` path — re-pin to a released version before release.
- The **demo dir is excluded** from this repo's own ruff/format targets (it is rendered output with its own tooling).

## CI (`.github/workflows/`)

- `tests.yml` — matrix over replay files (`stable`/`default`/`master`); starts the DB, lints, runs `tests/`.
- `demo-project.yml` — generate from `tests/replay/master` and run `setup-and-verify.sh`.
- `documentation.yml` — build the demo's Sphinx docs and deploy to GitHub Pages on push to `master`.

All workflows use Python 3.14 via `astral-sh/setup-uv`.

## Conventions

Ruff enforces the mechanical rules — run `uv run inv lint` rather than matching style by eye. It covers this repo's
own Python (`cookiecutter_extensions.py`, `dev/`, `tests/`, `tasks.py`) and then runs the template checks; the demo
is excluded, and verifies itself through `setup-and-verify.sh`.

## Commits

- **Group by area of concern:** one commit per concern; keep unrelated changes apart.
- **A version bump carries its mechanical fallout:** widened types, renamed arguments, and
  whatever else the new release needs to keep the suite and the type checker green belong in the
  bump commit, so it stands on its own. Behavioural work goes in its own commit.
- **Refine with `fixup!`, don't rewrite:** when a later change reworks an earlier commit, record it as a `fixup!`
  commit (`git commit --fixup=<sha>`) instead of amending the original.
- **Never rebase on your own:** don't run the autosquash — the unsquashed history is useful during development.
  Rebase only when explicitly instructed.
- **Isolate disposable notes:** keep scratch/working notes (e.g. an `adoption-notes/` folder or `claude-todos.txt`
  file) in their own standalone commits, separate from real code/docs, so they can be dropped later.
- **Write lean messages:** state the *why* and any non-obvious *what*; omit whatever the diff shows. Prefer a
  single-line message when the subject already conveys the why. No mechanical consequences (renames, updated
  references, call-site fixups), and no "verified"/"tests pass"/"build clean" lines.
- **Template ⇆ demo is one concern, two commits:** the template edits, then the regeneration
  (`chore: regenerate the demo`). Intermediate commits fail `tests/test_demo_in_sync.py`; that is expected and
  matches the existing history.
- **Run `uv run inv clean` after rewriting history:** a rebase changes file mtimes, and a stale `.mypy_cache` then
  makes `inv demo-verify` fail on imports that resolve fine from a clean state.
